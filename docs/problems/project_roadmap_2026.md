距离下次比赛约一年。

## 一、项目现状（诊断结果）

### 1.1 三方案架构

| 方案 | 传感器 | 定位方式 | 当前状态 |
|------|--------|---------|---------|
| Scheme1 纯相机 | 海康相机 | YOLO+透视变换/raycast | qnl在优化raycast，最新commit未合并 |
| Scheme2 融合 | 海康+Livox HAP | YOLO+点云投影聚类 | 最可运行，但有严重bug |
| Scheme3 空中 | Livox HAP | 背景减除+DBSCAN+Kalman | 基本可用，缺裁判系统对接 |

### 1.2 已发现的严重bug（4个，影响比赛结果级别）

1. **友方/敌方坐标未分流**（`radar.py:316`）— 所有检测结果（含己方）都通过0x0305敌方标记通道发送。己方坐标应走单独的上报通道（2026规则要求上报双方坐标）
2. **硬编码绝对路径**（`lidar_node.py:72`）— 写死了syh的机器路径`/home/syh/...`，换机器必崩
3. **TF失败回退矩阵错误**（`radar.py:182`）— 用`np.ones((4,4))`而非`np.eye(4)`，产生垃圾坐标
4. **空中launch缺节点**（`hnurm_air_launch.py`）— 未包含`judge_messager`，空中检测结果无法上报裁判系统

### 1.3 Git分支问题

- `radar.py`被**所有分支**修改，是合并的最大冲突点
- syh有4个分支重叠修改radar.py，需要整合
- qnl和syh各自独立创建了相似的跟踪模块（hungarian_tracker, bbox_kalman, guess_pts），代码重复
- develop已停滞，feature/add_rosbag是事实上的主干

### 1.4 已观察到的运行时现象

**rosbag 回放测试（全明星赛第一局）中发现：**

1. **视频画面卡顿**：rosbag 中 `/compressed_image` 仅 ~9.3 fps（3786帧/408秒），加上 YOLO 推理延迟，实际显示帧率更低，画面明显一卡一卡
2. **近处检测框闪烁**：近距离目标的检测框频繁出现/消失，原因：
   - 近处目标占满画面，YOLO 置信度不稳定（训练数据多为中远距离）
   - 跟踪器（ByteTrack/Hungarian）在置信度波动时反复丢失/重获目标
   - `radar.py:319` 的 `div_times = 1.01` 几乎未缩小检测框，近处大框内点云分散，DBSCAN 聚类容易失败导致该帧被跳过

> 这些属于 Phase 2/3 范围的优化项（跟踪模块稳定性 + 检测模型近距离泛化能力），非 Phase 0 紧急 bug。

### 1.5 裁判系统通信缺口

| 功能 | 状态 | 备注 |
|------|------|------|
| 敌方地面坐标上报(0x0305) | ✅ 已实现 | 核心功能 |
| 双倍易伤触发(0x0301→0x0121) | ✅ 已实现 | 每场最多2次 |
| 比赛状态/血量/标记进度接收 | ✅ 已实现 | |
| 敌方空中机器人坐标上报 | ❌ 未实现 | 2026赛季要求 |
| 己方地面/空中机器人坐标上报 | ❌ 未实现 | 2026赛季要求 |
| 信息波密钥提交 | ❌ 未实现 | 电控负责，得分权重最高(x200) |

### 1.6 得分公式

```
得分 = (准确标记秒数×1 + 反空中次数×20 + 信息波难度×200) / 总比赛秒数
```

标记惩罚是奖励的2倍（错误-10/s vs 正确+5/s），准确率必须 > 66% 才能维持标记。

## 二、行动计划（6个Phase，约12个月）

### Phase 0: 紧急Bug修复（第1周）

**目标**：消除所有已知的运行时崩溃和逻辑错误

| 序号 | 修改文件 | 修改内容 |
|------|---------|---------|
| 1 | `radar.py` | 敌方/己方坐标分流：敌方走0x0305标记通道，己方暂时只走display_panel显示 |
| 2 | `radar.py` | TF失败回退改为`np.eye(4)` |
| 3 | `radar.py` | 修复双重齐次化问题、去除重复日志 |
| 4 | `lidar_node.py` | 硬编码路径改为使用`paths.py`的`resolve_path`从config读取 |
| 5 | `hnurm_air_launch.py` | 添加`judge_messager`节点 |

**验证**：rosbag回放Scheme2全流程无崩溃；EKF输出坐标在赛场范围28m×15m内。

### Phase 1: 代码架构整理（第2-4周）

**目标**：解耦节点、统一数据流、为后续方案切换打基础

#### 1.1 节点职责梳理与解耦

当前问题：`radar.py`承担太多职责（点云融合+坐标变换+跟踪+过滤），导致每个分支都改它。

拆分计划：
- `radar.py` → 只负责融合决策和坐标输出
- 提取坐标变换逻辑 → `shared/transforms.py`
- 提取目标路由逻辑 → `shared/target_router.py`（敌方→标记通道，己方→己方上报通道，范围检查）
- 提取跟踪逻辑 → `shared/tracker.py`（统一Hungarian/ByteTrack接口）

#### 1.2 统一跟踪模块

qnl和syh各自创建了`hungarian_tracker.py`、`bbox_kalman.py`、`guess_pts.py`。评估两个版本的质量，选最好的放入`shared/`，三个方案共用。

#### 1.3 配置整理

- 合并/清理过多的`.yaml`配置文件
- 确保所有路径都通过`paths.py`管理，消除硬编码

#### 1.4 规范ROS2 Topic命名和消息定义

当前Topic命名不统一，趁重构统一规范。

**验证**：重构后rosbag回放三个方案全流程通过；所有节点独立可启动、可替换。

### Phase 2: 评估并吸收分支代码（第5-8周）

**目标**：把qnl和syh的有效优化选择性集成到主分支

#### 2.1 评估qnl的camera-scheme-v

- `camera_detector.py` — raycast定位方法 vs 透视变换，精度对比
- `bbox_kalman.py` — 自适应卡尔曼滤波器的参数调优
- 决定：raycast是否取代透视变换作为Scheme1默认方法

#### 2.2 评估syh的rosbag_radar

- `radar.py` 的 cluster-then-project 方法 vs 当前 project-then-cluster
- `tracker_enhanced.py` — 三轨迹融合的有效性
- `detector_node.py` 的3D坐标解算
- syh_lidar_2027分支中的文档是否有保留价值

#### 2.3 集成策略

**不使用git merge**，而是：
1. 审查每个文件的diff
2. 对有价值的改动，在add_rosbag分支上手动应用
3. 与Phase 1的架构重构配合，把优化放到正确的模块位置

### Phase 3: 确立目标架构——地面纯相机+空中LiDAR（第9-16周）

**目标**：Scheme1(纯相机)发展为地面主力方案，Scheme3(纯LiDAR)专注空中

#### 3.1 纯相机方案强化

- 整合qnl的raycast优化
- 升级YOLO模型（数据质量优先，考虑版本升级）
- 定位精度优化（透视变换/raycast参数调优）
- 坐标范围检查和异常值过滤

#### 3.2 空中方案完善

- 完善hnurm_air_launch.py（加入judge_messager）
- 背景减除鲁棒性优化（多环境测试）
- 接入裁判系统上报空中机器人坐标

#### 3.3 Scheme2保留为备选

融合方案不删除，但降低优先级。如果纯相机效果足够好，就不需要LiDAR做地面定位。

### Phase 4: 裁判系统重构（第12-16周，与Phase 3并行）

**目标**：补全所有通信功能，提高鲁棒性

新增功能：
1. 己方地面机器人坐标上报
2. 己方空中机器人坐标上报
3. 敌方空中机器人坐标上报
4. 异常处理和断线重连
5. 多机器人通信广播

前提：先阅读通信协议V1.3.0确认具体字段定义。

### Phase 5: 测试与质量保障（贯穿全过程）

**目标**：建立测试体系，避免"测不出来到赛场才出问题"

当前：仅39个测试，覆盖串口协议/标签映射/路径。需要补充：
1. 坐标变换单元测试（已知输入→预期输出）
2. EKF滤波器单元测试
3. 裁判系统通信集成测试
4. rosbag端到端回归测试（已有基础设施，缺自动化断言）
5. 定位精度基准测试（用标注好的数据集）

### Phase 6: 文档更新（收尾）

- 更新docs/与代码同步
- README更新
- 为新成员准备入门文档（如果罗霖/刘巧玲加入开发）
